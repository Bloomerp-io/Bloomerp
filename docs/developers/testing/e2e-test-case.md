# End-to-end test cases

Use `BloomerpE2ETestCase` when the contract requires a real browser. An
`E2ERequestScenario` describes initial state, authentication, a starting URL,
and an ordered series of `E2EAction` objects.

End-to-end tests are not generated by `generate_test_cases`; create them for
selected user journeys after the narrower model, field, widget, component, and
view layers are covered.

## Scenario structure

```python
from bloomerp.tests.base import (
    BloomerpE2ETestCase,
    E2EAction,
    E2ERequestScenario,
)


class TestTodoEditingE2E(BloomerpE2ETestCase):
    def get_test_scenarios(self) -> list[E2ERequestScenario]:
        todo = Todo.objects.create(title="Prepare report")

        return [
            E2ERequestScenario(
                name="Admin renames a to-do",
                user=self.admin_user,
                url=todo.get_absolute_url(),
                actions=[
                    E2EAction(
                        name="Change the title",
                        execute=self.input_field("title", "Send report"),
                        validators=self.expect_field_value("title", "Send report"),
                    ),
                    E2EAction(
                        name="Save",
                        execute=self.press_button_and_wait_for_response(
                            "Save",
                            todo.get_absolute_url(),
                            method="POST",
                            expected_status=200,
                        ),
                        validators=self.expect_database_value(
                            todo,
                            "title",
                            "Send report",
                        ),
                    ),
                ],
            )
        ]
```

Each scenario receives a fresh browser context, so cookies and browser storage
do not leak. `prepare` runs before authentication and navigation. `cleanup`
runs in a `finally` block even when an action fails.

## Actions and validators

An action contains a deferred zero-argument `execute` callback and optional
zero-argument validators. Actions execute in declaration order. The base wraps
failures with the scenario and action names, so name both precisely.

Reusable actions include navigation, filling or clearing Django fields,
selecting options, pressing buttons or keys, clicking, checking controls,
uploading files, and waiting for a response caused by a button press.

Reusable validators cover visibility, hidden state, visible text, field
values, the current URL, and refreshed database values. Playwright assertions
may return `None`; custom boolean validators may return `True` or `False`.
Use `custom_action()` for behavior that cannot be expressed by a helper.

## When to use end-to-end tests

Reserve this layer for browser integration: JavaScript events, HTMX requests
and swaps, navigation, focus, uploads, and complete user journeys. Server-side
status codes, fragments, JSON, and permissions are faster and clearer in
[view](view-test-case.md) or [component](component-test-case.md) scenarios.
