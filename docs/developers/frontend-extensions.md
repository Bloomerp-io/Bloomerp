# App-owned TypeScript frontends

Implementation apps can own frontend components and npm dependencies without
changing the framework. The first public API exports `BaseComponent`,
`registerComponent`, `getComponent`, `initComponents`, and `componentIdentifier`.
Internal framework component classes are not part of this initial compatibility
contract.

## Scaffold an app

Create a new app with a frontend:

```bash
bloomerp app init production --frontend
```

Or add a frontend to an existing app, including an app created by project init:

```bash
bloomerp app frontend production
```

The command refuses to replace existing frontend files. Backend-only apps do not
need Node.js or a frontend workspace.

The generated app contains:

```text
frontend/
    package.json
    vite.config.ts
    tsconfig.json
    ts/main.ts
    ts/components/Example.ts
    ts/styles.css
static/production/
    frontend.json
    frontend/                 # generated by npm run build
        manifest.json
        assets/...
```

Install the Django app normally. Its `static/<AppConfig.label>/frontend.json`
descriptor enables bundle discovery. If changing the Django label, update that
directory and the manifest's static namespace together.

## Register a component

```typescript
import { BaseComponent, registerComponent } from '@bloomerp/frontend';

class ProductionPlanner extends BaseComponent {
    /** Prepare the planner after its instance has entered the shared registry. */
    public override initialize(): void {
        this.element?.setAttribute('data-planner-ready', 'true');
    }
}

registerComponent('production:planner', ProductionPlanner);
```

Use it in a Django template:

```html
<div bloomerp-component="production:planner"></div>
```

Use namespaced IDs. Duplicate registration throws unless the caller explicitly
passes `{ override: true }` as the third argument. An override affects future
instances; it does not replace live instances already attached to elements.

Do not initialize from a constructor. Use `onAfterSwap()` to reconcile descendants
changed by HTMX, and release resources in `destroy()`. Existing core lifecycle
limitations still apply: arbitrary DOM removal does not automatically guarantee
`destroy()` is called. Components owning expensive resources should handle the
existing HTMX cleanup events as appropriate.

## Shared runtime and loading

The npm package supplies a runtime facade and TypeScript declarations generated
from the core API. The implementation's Vite configuration externalizes
`@bloomerp/frontend` and `@bloomerp/runtime`, including during development.

Django emits an import map resolving both names to the public module emitted by
the core Vite build. Core and extensions therefore share the component registry,
instance registry, base class, and HTMX dependency. Do not import framework source
paths or bundle a separate framework runtime.

Core registers its components and loads translations, then imports installed app
entries in Django app order. Component auto-initialization starts after those
imports settle. A failed extension is reported in the browser console while other
extensions and core continue loading. Registration must complete during entry
evaluation; do not defer it to unawaited background work.

Only the initial document shell loads bundles. HTMX fragments declare component
markup and use the already loaded runtime.

## Build and deploy

```bash
cd apps/production/frontend
npm install
npm run build
```

Commit the generated `package-lock.json`. App wheel builds run `npm ci` when that
lock exists, otherwise `npm install`, then `npm run build`. Compilation failures
stop packaging. Wheels include the descriptor and compiled static assets and omit
the frontend workspace and node_modules. Deployed instances do not need Node.js.
Django's existing collectstatic pipeline serves the files.

CSS imported by the app is included through the manifest, including styles from
statically imported chunks. Lazy chunks and assets keep Vite's relative URLs.
For Tailwind, configure a separate app build that scans its templates and source;
the published core CSS cannot anticipate implementation-only utility classes.

## Development servers

Run `npm run dev` in the app workspace. The generated server uses port 5174.
Configure local Django settings:

```python
BLOOMERP_FRONTEND_DEV_SERVERS = {"production": "http://localhost:5174"}
```

This setting is used only with `DEBUG=True`; production always requires compiled
assets. Multiple app servers need distinct ports. Run the core development server
on 5173, or set `BLOOMERP_CONFIG.vite_dev_server_url` to an empty string to use the
built core runtime with an app development server.

## Publishing the npm API

The existing main-branch release workflow aligns `@bloomerp/frontend` with the
Python version, builds and type-checks its public contract, checks the package
contents, and publishes versions that are absent from npm. The Python and npm
registry checks run independently so a rerun can finish a partially published
release.

Before the first release, ensure the publishing account controls the `@bloomerp`
npm scope and configure the GitHub `NPM_TOKEN` secret with publishing permission.
The workflow requests public access and provenance using npm's
[GitHub Actions publishing procedure](https://docs.npmjs.com/generating-provenance-statements/).
No registry credentials or package publication are performed by the scaffold.

Keep an app's npm API dependency at the deployed Python framework version. Existing
app workspaces are user-owned; upgrades do not rewrite their dependency versions.
